# 组织树接口技术设计文档

## 1. 总体方案

建议将本次设计拆为两条相互关联但职责独立的链路：

1. **组织目录链路：** MySQL 保存权威组织数据，ES 保存面向查询的组织索引；四个既有接口维持业务契约，新增懒加载组织树接口和 ES 全量同步接口。
2. **上报数据授权链路：** 登录用户上下文 → 识别机构类型 → 计算授权机构/网格集合 → 将授权条件注入扫楼/线索查询 → 执行列表、详情、统计、导出。ES 组织索引可用于快速计算机构关系，但上报记录本身是否适合由 ES 查询，必须由现有数据模型决定。

**重点原则：组织关系查询和业务数据授权不是一回事。** ES 能快速找到组织或其祖先/后代，并不自动保证上报记录有正确的机构关联字段，也不能替代服务端权限校验。

## 2. ES 组织索引设计

### 2.1 建议索引字段

以现有 `SysDept` 和真实数据库字段为准，索引字段可包括：

- `deptId`：稳定组织 ID。
- `parentId`：直接父节点 ID。
- `ancestors`：现有祖先路径（若当前字段语义稳定）。
- `deptName`：组织名称，支持关键词检索。
- `orgNum`：机构编码（若为业务稳定标识）。
- `orgType`：机构类型（以确认后的枚举/字典为准）。
- 树查询所需的排序字段、启用状态及必要的权限过滤字段。

实际字段名、类型、分词器、keyword 子字段、空值处理和唯一键应根据当前实体、数据库和 ES 版本确认，不应在没有核查的情况下直接假设。

### 2.2 查询与树懒加载

- `GET /dept/tree` 首次请求返回根节点或用户有权看到的顶层节点。
- 展开节点时按 `parentId` 查询直接子节点，按既有排序字段返回。
- 对搜索命中节点，计算并返回命中节点及所有祖先节点，方便前端定位；不默认返回命中节点的所有后代。
- 若根节点固定为“浙江省”，根节点选择规则应明确固定，不能只依赖关键词匹配。
- 对高频 `parentId`、机构编码和祖先路径查询设计合适的 keyword/精确匹配字段。
- 若节点是否有子节点需要由前端判断，服务端应提供可靠的子节点信息或使用前端已有的展开策略。

懒加载只改变加载时机，不改变树的业务层级、节点含义或既有接口响应约定。新增树接口应与前端树组件的字段要求对齐。

## 3. 四个既有接口的 ES 接入策略

### 3.1 `GET /dept/list`

1. 保留既有请求参数、筛选语义、排序及响应格式。
2. 根据查询场景由 ES 执行适合的组织检索。
3. 若调用方依赖完整实体或现有 SQL 特有逻辑，应在方案评审时明确由 ES 返回字段还是按 ID 回查 MySQL。
4. 校验总数、排序、空值、模糊匹配、分页边界与旧实现一致。

### 3.2 `POST /dept`、`PUT /dept`、`DELETE /dept/{deptId}`

MySQL 继续作为权威数据源。新增、修改、删除不能仅操作 ES。

建议链路：
1. 执行现有参数校验、权限校验及业务约束。
2. 先完成 MySQL 事务操作。
3. 可靠地更新 ES 文档：新增/修改写入最新文档，删除移除对应文档。
4. 对更新父节点或祖先路径的场景，评估是否需要同步更新相关子节点的冗余祖先字段。
5. 记录同步失败并提供重试或全量同步修复机制，避免数据库已成功但索引永久不一致。

若现有架构没有可靠的事务后事件/消息机制，可在实现阶段选择事务提交后同步、可靠事件表或现有消息设施；本设计阶段不预设引入新中间件。

## 4. 新增接口设计

### 4.1 `GET /dept/tree`

建议查询参数：
- `parentId`：父节点 ID；首屏根节点请求可不传。
- `keyword`：可选搜索词。
- `pageSize`：可选单次返回量。

处理步骤：
1. 从服务端认证上下文解析当前用户、角色、机构类型和机构 ID。
2. 根据权限确定可见组织范围。
3. 首次请求返回可见根节点；展开请求只查询该父节点的直接子节点。
4. 若带搜索词，检索命中组织，并补齐祖先链用于定位；不默认拉取全部后代。
5. 以稳定排序字段输出与前端现有树组件兼容的数据结构。

不得把请求参数中的 `parentId` 当作权限凭证。查询某个父节点的子节点之前，必须确认该节点在当前用户可访问范围内。若原有组织树对不同角色有不同展示范围，沿用已确认的业务规则，不擅自改变根节点和可见范围。

### 4.2 `POST /dept/es/sync`

处理步骤：
1. 校验管理员权限。
2. 从 MySQL 分批读取组织权威数据。
3. 映射成统一 ES 文档并批量写入新索引或目标索引。
4. 检查写入数量、失败条目和关键字段。
5. 全部成功后切换查询别名（如采用别名方案）；失败时保留旧可用索引并返回失败摘要。
6. 记录操作者、开始/结束时间、成功数量和失败信息。

必须限制接口权限，避免被普通业务账号触发大规模重建。

## 5. 核心设计：上报数据权限如何查询

### 5.1 统一授权上下文

在服务端形成统一的查询权限上下文，概念上包括用户/角色、当前登录用户所属机构 ID、`sys_dept` 中的机构类型，以及按机构类型计算出的数据范围。

当前登录用户及所属机构 ID 必须通过项目现有 `SecurityUtils.getLoginUser()` 获取，沿用其返回对象的实际结构，不新建或替换登录工具类。机构档案和网格相关数据从现有 `SysDept`/`sys_dept` 读取。前端传入的 `orgCode`、`gridCode` 或机构 ID 只能作为额外筛选条件，不能作为授权依据。

### 5.2 金监机构：通过管辖区编码确定网格范围

授权计算：

1. 调用 `SecurityUtils.getLoginUser()`，从现有登录用户对象取得当前用户所属机构 ID。
2. 使用该 ID 查询 `sys_dept` 中的金监机构档案，读取管辖区编码。
3. 根据网格编码以前缀匹配管辖区编码的规则，确定辖内网格。例如管辖区编码为 `3303` 时，网格编码以 `3303` 开头的网格属于该辖区。
4. 将辖内网格映射为上报记录实际使用的关联键，并在数据库查询执行前加入权限过滤。
5. 再与时间范围、状态、关键词等页面条件取交集。

逻辑示意（字段名为占位符，必须核对实际实体与 SQL）：

```sql
WHERE report.<实际网格关联字段> IN (<当前管辖区内网格对应的键集合>)
  AND <页面原有业务筛选条件>
```

金监局按管辖区编码自动确定可见网格，不依赖人工分配网格。管辖区编码、网格编码的真实字段名、编码格式及网格记录识别条件，须以 `SysDept` 实体和现有 SQL 为准。

### 5.3 银行机构：沿用现有权限与网格分配规则

授权计算：

1. 调用 `SecurityUtils.getLoginUser()` 获取当前登录用户所属机构 ID。
2. 使用该 ID 查询 `sys_dept` 中对应的银行机构。
3. 按现有网格分配规则确定分配给该银行机构的网格，并核实 `@DataScope` 的实际 SQL 是否同时控制当前机构、下级机构及网格范围。
4. 将授权范围转换为上报记录实际使用的关联键，在查询执行前过滤。

逻辑示意：

```sql
WHERE report.<实际网格或机构关联字段> IN (<现有权限规则计算出的键集合>)
  AND <页面原有业务筛选条件>
```

银行机构不可使用金监机构的管辖区编码前缀规则。不能只凭 `@DataScope` 注解存在就认为权限正确，必须核对最终 SQL 和网格分配规则；也不能未经确认自行扩大或缩小银行原有权限范围。

### 5.4 SQL、ES 还是混合查询

选择取决于上报数据当前存储方式：

- **上报数据仍在 MySQL：** 推荐将授权机构/网格集合转换成 SQL 条件，在数据库分页、统计和导出前过滤。ES 只负责快速获取组织/网格范围。
- **上报数据已经进入 ES：** 在 ES 查询 DSL 中使用 `terms` 过滤授权网格编码或机构编码，并在查询层强制加入；详情查询也需重新校验。
- **混合查询：** 先由组织索引计算授权集合，再把集合传入上报数据实际存储层执行过滤。不能先查出不受限数据再由前端过滤。

不得仅因为组织树接入 ES，就擅自把上报业务表迁移到 ES；数据存储改造不在当前已确认范围内。

### 5.5 两个 `list` 查询接口的具体改造设计（必改项）

本次明确要求修改以下两个页面的 `list` 查询接口，而不是只做代码审查：

- `BuildingSweepReportController`（路由前缀 `/building-sweep/report`）中，扫楼上报管理页面实际调用的 `list` 查询接口。
- `RiskClueReportController`（路由前缀 `/risk-clue/report`）中，线索上报管理页面实际调用的 `list` 查询接口。

由于方法名、参数对象、Mapper 方法及表字段必须以当前仓库代码为准，实施前先从前端页面调用处追踪到 Controller、Service、Mapper 和实际 SQL，确认两个 `list` 的真实调用链；不在设计阶段臆造未核实的方法名或字段名。

### `list` 接口处理流程

1. Controller 接收页面原有筛选参数，保留现有请求和响应结构。
2. 调用现有 `SecurityUtils.getLoginUser()` 获取登录用户及所属机构 ID，再从 `sys_dept` 读取机构类型和档案信息；不得把请求参数里的机构编码或网格编码直接当成授权依据。
3. 金监机构：读取管辖区编码，按网格编码前缀计算辖内网格；银行机构：按现有网格分配规则和已核实的 `@DataScope` SQL 计算范围。
4. 将授权集合传给 Service/Mapper，并与页面原有的时间、状态、关键字等条件取交集。
5. 在数据库执行查询时应用权限过滤，之后再计算总记录数、排序和分页结果。禁止先查询超出权限的数据再由 Java 或前端过滤。
6. 授权集合为空时，显式返回空分页结果或统一的权限错误；不得省略权限条件而返回全量数据。
7. 记录上报数据关联字段尚未核实前，先确认记录究竟关联网格编码、网格 ID、机构编码还是机构 ID，再选择实际 SQL 条件。若用网格 ID/机构 ID，须先将授权范围可靠地转换成相同类型的键。

### `list` 查询条件示意

金监机构账号：先从 `sys_dept` 读取当前机构管辖区编码，再筛选网格编码以前缀匹配该管辖区的网格，并按上报记录真实关联字段过滤。

```sql
WHERE report.<实际网格关联字段> IN (<当前管辖区内网格对应的键集合>)
  AND <页面原有筛选条件>
```

银行机构账号：按现有网格分配及 `@DataScope` 规则计算授权键集合后过滤。

```sql
WHERE report.<实际网格或机构关联字段> IN (<现有权限规则计算出的键集合>)
  AND <页面原有筛选条件>
```

以上为权限逻辑示意，`report`、字段名和键类型均为占位说明，不能直接复制为项目 SQL。最终条件需按两个模块的真实实体、关联字段、Mapper SQL 和数据库类型落地。

### `list` 接口验收重点

- 金监账号关联多个网格时，列表和分页总数均只覆盖所有授权网格，且不能漏掉其中任何一个。
- 银行账号列表覆盖本机构及全部下级机构，不含其他无关银行。
- 页面传入其他机构/网格筛选值只能进一步缩小结果，不能扩大授权范围。
- 无授权范围不返回全量；通过修改请求参数不能绕过服务端过滤。
- 同一筛选条件下，分页总数、统计和导出与相同授权口径保持一致。

## 5.6 页面所有查询入口的覆盖

逐一检查 `BuildingSweepReportController` 和 `RiskClueReportController` 下页面实际使用的接口及其 Service/Mapper：
- 列表、分页；
- 详情；
- 统计、汇总；
- 导出；
- 页面加载所需的其他查询。

每个入口都应复用统一的权限范围计算逻辑。分页总数必须在权限过滤后计算；统计和导出不能另走无权限条件的 SQL；详情根据记录真实所属网格/机构做授权校验。

对 `@DataScope` 应检查实际注入 SQL、机构层级规则、表别名、角色覆盖和各查询方法是否使用该注解。注解存在本身不构成已满足权限要求的证据。

## 6. 数据一致性与异常处理

- MySQL 是组织数据权威来源，ES 是可重建的查询索引。
- 写操作成功而 ES 更新失败时，应可观测、可重试，并能通过全量同步修复。
- 全量同步应有管理员权限、运行记录和失败报告。
- 用户无有效授权网格/机构时返回空结果或明确拒绝，不得移除过滤条件。
- 组织删除或移动时，评估下级祖先路径、缓存、关联关系和索引文档的同步。
- 对 ES 不可用的降级策略需在实现前确认；任何降级都不得绕过数据权限。

## 7. 验收测试矩阵

| 用户/场景 | 预期可见范围 |
|---|---|
| 金监机构 A 关联 G001、G002 | 仅能查到 G001/G002 的扫楼及线索记录 |
| 金监机构 A 关联多个网格 | 所有授权网格均可查询，不可只取一个网格 |
| 金监机构 A 请求未关联网格 G999 | 不得通过请求参数扩展到 G999 |
| 银行支行 A | 本机构及全部下级机构的记录 |
| 银行支行 A 查询无关银行 B | 不返回 B 的记录 |
| 无有效网格/机构授权的账号 | 空结果或明确拒绝，不返回全量 |
| 详情接口传入越权记录 ID | 拒绝或按项目统一方式返回无权限结果 |
| 统计/导出 | 与同筛选条件下授权列表范围一致 |
| 组织树首次加载 | 只返回根节点/顶层节点 |
| 展开组织节点 | 仅加载该节点的直接子节点 |
| 组织索引全量同步 | ES 文档与 MySQL 权威组织数据一致 |

## 8. 实施前必须核实的内容

1. `SysDept` 实际字段及 `ancestors` 的编码格式、机构编码唯一性。
2. 两个上报模块的实体、Mapper SQL、列表/详情/统计/导出完整接口清单。
3. 上报记录真实关联网格或机构的字段与映射关系。
4. `SecurityUtils.getLoginUser()` 返回对象中所属机构 ID 的真实获取路径。
5. `SysDept`/`sys_dept` 中机构类型、管辖区编码、网格编码及网格记录识别条件的真实字段名。
6. 银行网格分配关系来源，以及 `@DataScope` 对机构层级和网格范围的实际 SQL 行为。
7. ES 版本、现有客户端、索引部署方式与故障降级要求。

上述内容核实后再细化到真实字段、Mapper 条件与代码修改点；本文件不假定尚未核实的表名或字段名。
