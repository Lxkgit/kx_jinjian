# 组织树接口改造需求文档

## 1. 项目目标

本次改造包含组织树查询性能优化和上报业务数据权限适配两项工作，其中**重点是明确并落地不同机构用户的数据可见范围**。

- 组织树：通过 ES 提升组织查询效率，前端按需懒加载；保留原有组织业务结构及接口行为。
- 上报查询：对“扫楼上报管理”和“线索上报管理”页面的服务端查询入口统一适配机构权限。
- 当前阶段：需求设计；不包含代码实现、数据库变更执行和生产部署。

## 2. 组织树接口需求

### 2.1 改造四个既有接口

| 接口 | 需求 |
|---|---|
| `GET /dept/list` | 接入 ES 查询能力，保留原查询参数和响应格式；需支持既有列表查询语义。 |
| `POST /dept` | 保留新增组织业务行为；MySQL 成功写入后同步 ES，避免索引与数据库长期不一致。 |
| `PUT /dept` | 保留修改组织业务行为；更新后同步 ES，并处理组织名称、父级或祖先路径变化造成的索引更新。 |
| `DELETE /dept/{deptId}` | 保留删除校验和业务行为；删除成功后同步删除 ES 文档，并处理子级组织、关联数据等现有约束。 |

既有接口的 URL、参数、响应结构和错误语义应保持兼容。ES 是查询索引，不替代 MySQL 作为权威数据源；写操作不应只写 ES。

### 2.2 新增两个接口

#### A. `GET /dept/tree` —— 当前用户可见的组织树节点

用于组织树懒加载，并根据当前账号的角色/机构权限限制可见范围。

建议参数：
- `parentId`：父节点 ID；首次加载根节点时可不传或按系统固定根节点规则处理。
- `keyword`：可选搜索关键词（若需要支持树搜索）。
- `pageSize`：可选单次返回节点数量，默认值由实现统一约定。

要求：
- 首次只返回根节点或当前用户有权查看的顶层节点。
- 展开节点时按 `parentId` 加载其直接子节点，不一次性返回整棵树。
- 搜索结果需返回命中节点及其完整祖先链，以便前端定位；不默认返回所有后代。
- 根节点规则保持现状（业务要求固定浙江省时，不得因 ES 查询而改变）。
- 返回字段和原前端树组件所需字段兼容；是否有子节点应根据可靠数据判断，避免前端因缺少提示而无法展开。
- 权限范围由服务端从登录上下文确定，不能信任客户端传入的机构编码作为授权依据。

#### B. `POST /dept/es/sync` —— 组织索引全量同步

用于初始建索引、修复索引或人工触发全量覆盖同步。

要求：
- 只允许有权限的管理员调用。
- 从 MySQL 读取权威组织数据，按约定映射重建/覆盖 ES 索引。
- 返回成功/失败状态、处理数量及必要的错误摘要；记录操作人和执行结果。
- 同步过程中应考虑失败恢复与索引切换，避免失败后查询索引出现长期空缺。
- 不允许普通用户通过该接口任意写入组织文档。

## 3. 上报查询权限适配需求

### 3.1 涉及页面

- 扫楼上报管理：`BuildingSweepReportController`，`/building-sweep/report`。
- 线索上报管理：`RiskClueReportController`，`/risk-clue/report`。

**两个页面的 `list` 列表查询接口属于本次明确改造范围，必须实际修改其服务端查询逻辑。** 不只是评估或检查，也不能只改详情、统计或导出。

- `BuildingSweepReportController`（`/building-sweep/report`）中的页面 `list` 查询接口：增加当前登录用户的数据权限过滤。
- `RiskClueReportController`（`/risk-clue/report`）中的页面 `list` 查询接口：增加当前登录用户的数据权限过滤。

具体 `list` 方法签名及其 Service/Mapper 查询语句应以仓库当前代码为准，在实施前逐项定位确认，不凭空假设方法名或数据库字段。除上述两个必改 `list` 接口外，还须逐项梳理页面实际调用的详情、统计、导出及其他查询接口，确保不会从其他入口绕过权限。

### 3.2 金监机构账号

- 通过现有 `SecurityUtils.getLoginUser()` 获取当前登录用户，并从登录用户对象取得所属机构 ID。
- 根据所属机构 ID 查询 `sys_dept` 中的金监机构档案，读取管辖区编码。
- 按网格编码以管辖区编码为前缀的规则，确定辖内网格；省级 2 位、市级 4 位、区县级 6 位编码均按前缀覆盖下级区域。
- 扫楼/线索上报查询必须在服务端将辖内网格范围落实为查询条件。
- 不额外假定存在人工维护的金监机构—网格关联表；网格数据以现有 `sys_dept` 数据和已确认业务规则为准。实际字段名以 `SysDept` 实体及 SQL 核实结果为准。

### 3.3 银行机构账号

- 通过 `SecurityUtils.getLoginUser()` 获取当前登录用户所属机构 ID，再查询 `sys_dept` 中对应的银行机构。
- 银行机构的数据范围沿用现有权限规则，重点核实 `@DataScope` 的实际 SQL 与网格分配关系；银行仅能查看分配给本机构的网格及其业务数据。
- 若既有系统确实按机构层级控制下级机构可见范围，应以现有 SQL 为准保留该规则；不能未经核实就把所有下级机构等同于已授权网格，也不能扩大到无关银行。

### 3.4 查询入口与安全要求

所有页面查询入口均由服务端应用同一套权限规则：

- **两个页面的 `list` 列表/分页接口（明确必改）：** 在服务端查询条件中加入授权范围，先过滤权限，再计算总数和分页结果；不能只在前端过滤。
- 详情：按记录真实关联的网格/机构校验权限。
- 统计：统计口径与列表权限范围一致。
- 导出：导出数据必须使用与列表相同的权限条件，不能绕过权限查询全量数据。
- 其他页面实际调用的查询接口：逐一检查并纳入同一权限策略。

页面提交的机构或网格筛选项只能缩小服务端计算出的权限范围，不能扩权。授权范围为空时禁止退化为无条件查询。

## 4. 数据关联前置核查

正式确定 SQL/ES 查询实现前，需确认 `SecurityUtils.getLoginUser()` 返回对象中所属机构 ID 的获取路径，检查 `SysDept` 实体/`sys_dept` 中机构类型、管辖区编码、网格编码等真实字段，以及扫楼/线索记录的实际关联字段。不得新建重复登录工具类或假定存在独立网格关联表。

不得假设现有 `@DataScope` 已覆盖全部场景。必须验证注解最终生成的 SQL、适用角色、表别名及其对分页、详情、统计、导出接口的覆盖情况。

## 5. 验收标准

1. 组织树初次加载不返回整棵树，展开时按需加载子节点。
2. 四个既有接口的外部契约与业务功能保持兼容。
3. ES 初始全量同步后，组织查询结果与 MySQL 权威数据一致。
4. 新增、修改、删除组织后，索引能按设计同步更新。
5. 金监账号关联多个网格时，可以查到所有授权网格下的数据，也查不到未授权网格数据。
6. 银行账号可以查询本机构及全部下级机构数据，不能查询无关银行数据。
7. 列表、详情、统计、导出使用相同权限口径。
8. 通过篡改请求参数不能扩大可见数据范围。
9. 无授权范围时不会返回全量数据。

## 6. 本次不包含

不调整组织树业务层级，不变更既有四个接口契约；不在本次范围内实现网点菜单下线、机构档案新增字段、网格自动分配、多家责任银行分配等独立需求；不直接执行生产数据迁移或部署。
