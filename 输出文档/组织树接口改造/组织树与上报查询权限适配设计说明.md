# 组织树性能优化与上报查询权限适配设计说明

## 1. 文档说明

- **项目：** 浙江省金监局防非打非网格系统
- **文档定位：** 本次改造的统一设计说明，合并原组织树需求理解、组织树改造需求及组织树技术设计三份文档。
- **当前阶段：** 需求与设计阶段，仅整理设计，不开发代码、不执行数据库变更。
- **核心结论：** 本次重点是适配扫楼上报、线索上报两个页面的数据查询权限。组织树本身不调整业务功能和接口契约，只进行不影响接口功能的查询性能优化。

## 2. 改造背景与总体范围

此前将本次工作理解为组织树接口改造，但进一步确认后，本次主要目标是让不同类型机构的用户，在扫楼上报和线索上报页面中查询到符合其业务权限的数据。

本次设计分为两个部分：

1. **组织树性能优化：** 保留现有组织树的业务行为、组织结构、接口路径、请求参数和响应格式，只优化内部查询性能，不改变调用方可观察到的接口功能。
2. **上报页面查询权限适配：** 对扫楼上报管理和线索上报管理两个页面实际使用的相关查询接口，设计金监机构与银行机构两套数据范围规则。

本次涉及的控制器：

| 功能页面 | 控制器 | 路径前缀 |
|---|---|---|
| 扫楼上报管理 | `BuildingSweepReportController` | `/building-sweep/report` |
| 线索上报管理 | `RiskClueReportController` | `/risk-clue/report` |

本次不自动扩展至其他业务页面或模块。网点管理菜单处置、多家责任银行网格分配、机构档案字段调整等高层需求，属于系统改造中的其他工作项；除非后续明确纳入本次范围，不在本文中设计其接口或实现细节。

## 3. 组织树：仅进行不改变接口功能的性能优化

### 3.1 保持不变的内容

组织树的现有业务功能和接口契约保持不变，包括：

- 现有组织层级及组织父子关系。
- 现有接口路径、HTTP 方法、请求参数和响应结构。
- 现有组织树展示、展开、搜索等业务行为。
- 现有调用方的使用方式，不要求前端因本次性能优化而修改。
- 现有组织数据的业务含义及维护方式。

组织内部关系继续以系统自身的组织字段为准，例如 `dept_id`、`parent_id`、`ancestors`。第三方机构编号（如 `org_num`、`parent_org_num`）不用于推导系统内部父子关系。

### 3.2 性能优化目标

组织树查询存在数据量较大、查询耗时偏长的问题。本次可在不改变接口行为的前提下优化内部查询过程，例如评估查询语句、索引、数据读取和结果组装效率。

具体优化方式应在查看现有实现和执行性能分析后确定，不在需求阶段预设必须采用某个中间件、索引结构或重写方案。不得为了性能优化改变接口原有的数据范围、节点内容、排序规则或错误处理行为。

### 3.3 性能优化验收原则

- [ ] 相同请求在优化前后保持原有业务语义和响应契约。
- [ ] 组织父子关系、搜索结果含义及权限范围不发生变化。
- [ ] 通过基线测试对比接口响应耗时和查询资源消耗。
- [ ] 性能优化不要求调用方修改接口调用方式。
- [ ] 如实施方案确需调整接口契约或前端行为，应另行确认，不视为本次已授权范围。

## 4. 上报页面查询权限规则

### 4.1 总体原则

扫楼上报和线索上报两个页面应根据当前登录用户所属机构类型，采用不同的数据查询范围：

- **金监机构：** 根据当前金监机构关联的网格编码集合查询。
- **银行机构：** 根据当前所属银行机构及其全部下级银行机构查询。

两类权限规则不能混为一套，也不能仅依据用户所属组织节点直接筛选所有业务数据。

### 4.2 金监机构用户

金监机构用户在扫楼上报、线索上报页面中，可以查询其关联的全部网格范围内符合页面原有筛选条件的事件。

具体规则：

1. 查询权限以网格编码为依据。
2. 一个金监机构可以关联多个网格编码，查询时需要支持多个编码组成的范围。
3. 查询结果覆盖这些网格范围内的相关事件，不限于当前金监机构用户或机构直接提交的事件。
4. 不得查询关联网格范围之外的事件。
5. 本文针对这两个上报页面使用网格编码确定查询范围，不使用行政区划管辖区编码替代网格编码。
6. 金监机构与网格的关联来源，以及上报事件与网格编码的关联字段，需要结合现有数据模型核对；不能假定这些关联一定已经存在。

### 4.3 银行机构用户

银行机构用户在两个页面中，可以查询当前所属银行机构及其全部下级银行机构对应的事件。

具体规则：

1. 查询范围包括当前所属银行机构本身及所有层级的下级银行机构。
2. 例如，分行用户可以查询本分行及其下属支行对应的事件。
3. 不得查询当前机构及其下级机构范围以外的其他银行事件。
4. 下级机构应依据系统内部组织关系识别，不能通过第三方机构编号推导父子关系。
5. 银行用户不套用金监机构的多网格查询规则，也不能仅因为银行位于某金监机构关联的网格内，就查询该网格范围内其他银行的事件。

## 5. 需要核查的接口范围

本次只设计以下两个页面实际使用的相关查询接口：

- `BuildingSweepReportController`（`/building-sweep/report`）下相关查询接口。
- `RiskClueReportController`（`/risk-clue/report`）下相关查询接口。

设计实施前，应结合两个控制器的实际方法和前端调用关系形成接口清单。不能仅凭控制器路径假定具体方法或 URL。

核查范围包括：

1. 页面列表查询。
2. 页面实际调用的详情查询。
3. 页面实际调用的统计、报表或导出查询。

只有页面实际使用的相关查询接口才纳入本次设计，不自动扩展到其他模块。对于不涉及页面查询的数据写入接口，不因本次需求而默认改变。

两个页面的相关查询入口应遵循一致的数据范围规则，避免列表已经过滤权限，但详情、统计或导出接口仍可返回超出范围的数据。

## 6. 服务端权限设计要求

### 6.1 权限必须在服务端生效

数据范围必须落实到服务端实际查询逻辑，不能只在前端隐藏数据。客户端传入的机构 ID、网格编码或其他筛选参数不能扩大当前用户的授权范围。

服务端应根据当前登录用户的身份和所属机构，确定用户类型及对应查询范围；客户端参数最多只能进一步缩小查询结果。

### 6.2 与现有 `@DataScope` 的关系

项目现有 `@DataScope` 机制是否能直接覆盖本次规则，需要核对对应方法、Mapper SQL、数据表关联和实际过滤条件。

- 如果现有机制能够准确表达相应范围，可以评估复用。
- 如果现有部门数据权限无法表达“金监机构关联多个网格编码”和“银行机构及全部下级机构”两套规则，则需要在后续技术设计中明确补充服务端过滤方式。
- 不能因为方法上添加了 `@DataScope` 注解，就认定权限过滤已经生效；必须确认实际 SQL 或查询流程确实应用了对应条件。
- 本文不预设尚未核实的数据库表名、字段名、Mapper 名称或 SQL。

### 6.3 数据关联依赖

进入代码实施前，应确认：

1. 当前登录用户如何关联到其所属机构及机构类型。
2. 金监机构如何关联一个或多个网格编码。
3. 扫楼上报事件如何关联网格编码。
4. 线索上报事件如何关联网格编码。
5. 上报事件如何关联银行机构，以及如何覆盖下级银行机构的数据。
6. 两个页面的详情、统计和导出等查询是否复用同一数据范围规则。

如果现有数据模型缺少必要关联，应先记录为待确认的设计依赖，不得通过放开查询范围来绕过问题。

## 7. 设计验收标准

### 7.1 组织树性能优化

- [ ] 组织树接口的现有路径、请求参数、响应格式及业务行为保持不变。
- [ ] 组织结构和组织父子关系保持不变。
- [ ] 查询性能有基线和优化后对比结果。
- [ ] 性能优化不造成数据范围扩大、节点缺失或搜索语义变化。

### 7.2 金监机构权限

- [ ] 一个金监机构关联多个网格编码时，扫楼上报和线索上报均能查询这些网格范围内的相关事件。
- [ ] 查询范围不限于当前金监机构自己提交的事件。
- [ ] 金监机构无法查询未关联网格范围内的事件。
- [ ] 权限判定使用网格编码，而非将行政区划管辖区编码当作网格编码。

### 7.3 银行机构权限

- [ ] 银行用户能查询当前所属银行机构及其全部下级银行机构对应的事件。
- [ ] 银行用户无法查询其他无关银行机构的事件。
- [ ] 银行权限不因金监机构的网格范围而扩大。

### 7.4 两个页面的接口一致性

- [ ] 已梳理两个控制器中页面实际调用的相关查询接口。
- [ ] 列表、详情及页面实际使用的统计、报表或导出接口均经过权限范围核查。
- [ ] 权限过滤在服务端实际执行。
- [ ] 修改客户端查询参数不能突破当前用户的授权范围。

## 8. 明确不在本文实施范围内的事项

以下事项不因本文而自动进入组织树或上报查询权限改造：

- 改变组织树层级、接口路径、请求参数或响应结构。
- 新增组织树业务接口或改变现有接口功能。
- 改变机构档案的字段、必填规则或数据维护流程。
- 网点管理菜单下线、网点数据迁移或旧网点表清理。
- 网格自动落格、金监机构网格自动归属及银行网格分配。
- 一个网格分配给多家责任银行的功能改造。
- 除扫楼上报、线索上报两个页面外的其他业务模块权限改造。
- Java 代码开发、数据库变更、部署和实际性能调优操作。

如上述事项需要实施，应依据已确认的高层需求单独确定范围和设计文档，不与本次两个页面的查询权限适配混为一谈。

## 9. 本次设计结论

本次工作的重点是**扫楼上报和线索上报两个页面的数据查询权限适配**，而不是重新设计组织树。

组织树只进行不改变接口功能的性能优化；上报页面则按机构类型采用不同查询范围：金监机构按其关联的多个网格编码查询，银行机构按当前所属银行及其全部下级机构查询。权限必须在服务端生效，且需要核实两个页面实际查询接口及相关数据关联后，才能进入代码实施阶段。
