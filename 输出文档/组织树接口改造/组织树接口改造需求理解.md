## 一、需求背景与现状

部门管理页面及组织树在数据量较大时存在响应问题，当前提出的原因有两类：

1. **接口查询响应慢：** 当前接口加载耗时约 1.67 秒。
2. **前端数据量过大：** 一次性返回较多组织数据，导致页面加载和交互响应变慢。

目前的判断是：继续使用 Elasticsearch（ES）优化组织数据查询，并通过组织树懒加载减少每次请求和页面初始化时需要加载的数据。

需要区分两类问题的解决方向：

- ES 主要用于优化服务端查询响应速度，目标是改善接口查询耗时。
- 懒加载用于避免一次性加载全部组织节点，按需查询下级节点，减少接口传输量和前端渲染压力。

因此，ES 与懒加载解决的问题不同，本次理解为两者都要采用，而不是二选一。

## 二、组织树结构理解

组织树需要同时表达行政区域层级、金融监管机构层级和银行机构层级。当前给出的结构示例为：

```text
浙江省
├── 浙江省金融监管局
│   └── 杭州市金融监管分局
│       └── 萧山区金融监管支局
├── xx银行
│   └── xxx分行
│       └── xxx支行
└── xx银行
```

当前理解：

- 浙江省作为上层节点。
- 浙江省金融监管局及其下属监管机构按监管组织关系形成层级。
- 银行及其总行、分行、支行按银行机构关系形成层级。
- 组织树应基于机构表中的父子关系组织节点，而不是仅将省、市、区行政区划机械地套用到所有银行节点上。
- 行政区域节点、监管机构节点和银行机构节点在业务上如何挂接，应以用户给出的实际机构数据和业务规则为准；不能仅凭名称推断父子关系。

## 三、机构数据来源与字段

现有机构表为 `sys_dept`，包含组织树所需的大部分数据，例如：

- `dept_id`：系统内部主键。
- `parent_id`：上级机构 ID。
- `ancestors`：祖级路径。
- `dept_name`：机构名称。
- `org_num`：机构编号。
- `address`：机构地址。
- `duty_name`：负责人名称。
- `duty_telephone`：负责人固定电话。
- `duty_phone`：负责人移动电话。
- `lng`、`lat`：经纬度。
- `area_code`：可视区域编码，是否直接作为“所属网格”需要进一步确认。
- `dot_type`：现有银行机构类型字段，当前注释为 1-人行、2-金融机构、3-网点。
- `dot_introduce`：现有介绍字段。
- `dept_classify`：银行机构分类。

用户希望组织树节点包含以下业务字段：

1. 机构名称
2. 机构号（使用业务机构编号，不是系统内部主键）
3. 机构地址
4. 机构负责人
5. 负责人固定电话
6. 负责人移动电话
7. 机构经纬度
8. 所属网格
9. 上级机构
10. 机构类型（省/市/区/总/分/支）
11. 机构介绍

当前字段对应关系的初步理解：

| 展示字段 | 现有字段或来源 | 说明 |
|---|---|---|
| 机构名称 | `dept_name` | 已存在 |
| 机构号 | `org_num` | 使用业务机构编号，不使用 `dept_id` |
| 机构地址 | `address` | 已存在 |
| 机构负责人 | `duty_name` | 已存在 |
| 负责人固定电话 | `duty_telephone` | 已存在 |
| 负责人移动电话 | `duty_phone` | 已存在 |
| 机构经纬度 | `lng`、`lat` | 已存在 |
| 所属网格 | 待确认，可能涉及 `area_code` 或其他网格关联数据 | 不能直接认定字段含义 |
| 上级机构 | `parent_id` 对应的上级机构数据 | 可用于组织层级关系 |
| 机构类型 | 新增 `org_type` | 用于区分省/市/区/总/分/支 |
| 机构介绍 | 新增 `org_introduction` | 用于保存机构介绍 |

注意：`dept_id` 是系统内部主键，不能作为业务展示中的机构号；机构号应使用 `org_num`。

## 四、已提出的数据库字段调整

用户此前提出增加以下字段：

## 五、接口改造范围

此前讨论中已确定：本次需要调整四个现有接口，并新增一个根据当前登录账号角色返回组织树的接口。

根据此前查看的 `SysDeptController`，目前可能涉及的四个现有接口为：

1. `GET /dept/list`：部门列表。
2. `GET /dept/list/exclude/{deptId}`：排除指定部门及其子级的部门列表。
3. `GET /dept/selectDeptTree`：组织树查询。
4. `GET /dept/pilotCenterPart/networkList`：支行列表。

以上四项是根据已查看的控制器方法整理的候选清单，仍需用户确认它们是否就是此前确定的四个接口。

此外，新增接口的目标是：

- 根据当前登录账号的角色和相应业务规则返回组织树。
- 组织数据从 ES 获取。
- 支持懒加载：初次请求只返回当前层级或根节点，展开节点时再请求对应下级节点。
- 返回满足前端展示需要的组织字段，并提供判断节点是否还有下级的必要信息。
- 具体 URL、请求参数、响应结构和角色数据范围尚待确认。

仓库中还存在 `GET /role/deptTree/{roleId}` 等角色配置相关接口，但目前不能据此认定它属于上述四个接口中的一个。

## 六、ES 与懒加载的当前理解

### ES

- 组织树查询数据需要从 ES 获取。
- ES 的主要目标是优化查询响应时间，针对当前接口约 1.67 秒的响应耗时进行优化。
- 需要确认现有 ES 索引是否已包含所需字段、索引如何同步 `sys_dept` 数据，以及新增字段是否需要同步进索引。
- ES 的具体查询方式、索引结构和同步机制属于后续技术设计，不在本阶段擅自定案。

### 懒加载

- 不应在首次进入页面时一次性加载全部组织节点。
- 前端展开某个组织节点时，再请求该节点的下级组织。
- 接口应能支持按上级机构标识查询直接子节点。
- 应避免为每次展开都返回整棵子树，否则无法达到懒加载减少数据量的目的。
- 是否支持关键字搜索、分页、默认展开层级，以及搜索结果如何定位到树节点，需要进一步确认。

## 七、当前理解中尚待确认的事项

1. 上述四个候选接口是否就是本次确定要修改的四个接口。
2. 组织树根节点的规则：是否始终以省份为根，还是根据当前账号角色返回不同层级的根节点。
3. 监管机构与银行机构之间的挂接规则，以及省/市/区与总/分/支类型是否完全按 `org_type` 区分。
4. “所属网格”具体对应哪个字段或关联表；`area_code` 是否就是所需的网格编码。
5. `org_type` 和 `org_introduction` 是否确认新增；若新增，旧数据如何补齐，ES 索引如何同步。
6. 新增接口的 URL、请求参数和响应格式。
7. 角色如何限制组织树范围；多角色账号、特殊角色和无权限情况如何处理。
8. 懒加载接口是否还需要支持组织名称搜索，以及搜索时的返回规则。
9. 组织树节点是否每次都返回全部展示字段，还是列表只返回树节点必要字段、展开详情时再取完整信息。

## 八、当前阶段结论

当前需求理解是：**组织树数据通过 ES 查询，并通过懒加载避免一次性加载大量组织；组织层级按照实际机构关系组织，同时返回约定的机构业务字段；另外需要改造四个既有接口，并新增一个依据当前登录账号角色返回组织树的接口。**
