# 组织树接口改造需求理解

## 一、这次要解决什么问题

本次不是把组织树整体重做，也不是单纯新增一套树接口。目标分为两部分：

1. **组织树性能优化：** 保留原有组织结构、业务含义和接口兼容性，引入 Elasticsearch（ES）辅助组织查询；前端组织树采用懒加载，初次只取根节点或当前层级，展开时再加载子节点，避免一次返回并渲染整棵大树。
2. **上报数据查询权限适配：** 这是本次设计重点。扫楼上报管理、线索上报管理两个页面，需要根据当前登录用户所属机构类型，确定其能查询哪些上报记录。权限必须在服务端查询链路中执行，不能只靠前端隐藏数据。

本次仅输出设计文档，不编写 Java 代码、不执行数据库结构变更或部署。

## 二、组织树接口范围

### 2.1 需要改造的四个既有接口

- `GET /dept/list`：组织列表查询。
- `POST /dept`：新增组织。
- `PUT /dept`：修改组织。
- `DELETE /dept/{deptId}`：删除组织。

四个接口保持原有 URL、参数和响应契约。ES 用于提升组织查询能力；MySQL 仍作为组织数据的权威数据源，新增、修改、删除先保证数据库事务成功，再同步或可靠更新 ES，不能把 ES 当作唯一数据源。

### 2.2 需要新增的两个接口

- `GET /dept/tree`：根据当前登录用户的角色和机构范围返回组织树节点，支持按父节点懒加载。
- `POST /dept/es/sync`：组织数据全量同步/重建 ES 索引的管理接口，应限制为有权限的管理员调用，并记录同步结果。

不新增第三个接口。组织树懒加载通过 `GET /dept/tree` 的查询参数实现；权限树的范围由当前登录账号确定，客户端不能自行提交一个机构 ID 就获得该机构权限。

## 三、上报数据可见范围

涉及页面及后端模块：

- 扫楼上报管理：`BuildingSweepReportController`，路由前缀 `/building-sweep/report`。该页面的 `list` 列表查询接口是本次明确需要修改的接口。
- 线索上报管理：`RiskClueReportController`，路由前缀 `/risk-clue/report`。该页面的 `list` 列表查询接口是本次明确需要修改的接口。

两个 `list` 接口必须在服务端查询阶段应用当前登录用户的数据权限，不能只改前端，也不能只调整详情或导出接口。具体方法签名、请求参数和对应 Service/Mapper 需结合仓库现有代码核对，不在未核查前臆造方法名。

### 3.1 金监机构用户

通过项目现有 `SecurityUtils.getLoginUser()` 获取当前登录用户，并从其现有对象结构中取得所属机构 ID；再使用该 ID 查询 `sys_dept` 中的机构档案，读取金监机构的管辖区编码。

金监机构可见网格按管辖区编码前缀确定，不是要求人工维护一份机构—网格关联清单。例如管辖区编码为 `3303` 时，辖内网格编码以 `3303` 开头；区县级编码 `330301` 则覆盖该前缀对应的网格。最终应按上报记录实际保存的网格关联键过滤数据。

### 3.2 银行机构用户

通过 `SecurityUtils.getLoginUser()` 获取当前登录用户所属机构 ID，再查询 `sys_dept` 中对应的银行机构。银行机构的数据范围沿用现有权限规则，重点核实 `@DataScope` 的实际 SQL 与网格分配关系；银行只能查看分配给本机构的网格及其业务数据。

若现有系统还按机构层级控制当前机构及下级机构的可见范围，应以实际生效的权限 SQL 为准，确认后保留；不能未经核实就将“所有下级机构”直接等同于全部可见网格。

### 3.3 权限的共同规则

- 当前用户身份、角色、机构类型和授权范围均由服务端认证上下文获取。
- 页面传入的机构、网格、组织筛选条件只能进一步缩小数据范围，不能覆盖或扩大服务端授权范围。
- 列表、分页、详情、统计、导出等页面实际使用的查询入口都必须执行相同的数据权限规则。
- 空授权范围默认返回空结果或明确的权限错误，不允许省略权限条件后退化为全量查询。
- 金监机构使用网格编码授权；银行机构使用当前银行机构及其下级机构授权。两套规则不可混用。

## 四、重点设计问题：怎样让不同机构用户看到正确的数据

查询链路应按以下顺序设计：

1. 从登录上下文识别用户所属机构、机构类型及角色。
2. 使用所属机构 ID 查询 `sys_dept`，读取机构类型及对应档案信息。
3. 金监机构按管辖区编码前缀计算辖内网格；银行机构沿用现有网格分配和 `@DataScope` 规则，并核实其实际生效范围。
4. 将服务端计算得到的授权范围转换为查询过滤条件。
4. 将授权条件与页面的时间、状态、关键字等业务筛选条件取交集。
5. 在两个 `list` 接口调用的 Service/Mapper 查询执行前注入权限条件；先完成权限过滤，再计算分页总数并取分页数据。统计和导出也使用同一授权范围。
6. 详情接口按记录所属网格/机构重新校验，不能仅凭前端提供的记录 ID 直接返回。
7. 以金监多网格、银行父子机构、无授权范围、跨机构详情、导出和统计作为验收用例。

`sys_dept` 中已有机构档案和网格相关数据，因此应优先核对现有 `SysDept` 实体及表字段，确认机构类型、管辖区编码、网格编码和网格记录识别规则。还需核对上报记录真实关联字段。ES 可用于组织/网格检索，但不能假设存在独立的机构—网格关联表，也不能臆造尚未核实的字段名。

## 五、设计边界

本次不改变组织树业务层级，不改变既有四个接口的外部契约，不新增与本次目标无关的业务功能。网点管理菜单、机构档案扩字段、网格自动分配、多家责任银行网格分配等内容不在本次方案内，除非另行确认。
