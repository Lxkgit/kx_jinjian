# 组织树接口改造——需求理解草稿（已补充技术约定）

> **文档用途：** 本文记录当前对需求的理解，供用户确认、纠正或补充。本文记录需求理解和已确认的技术约定；不代表已修改业务代码或执行数据库 SQL。

## 一、需求背景与目标

部门管理页面及组织树在数据量较大时存在两类性能问题：

1. **接口查询耗时较长：** 当前接口加载耗时约 1.67 秒。
2. **页面数据量较大：** 一次性加载大量组织节点会增加传输量和前端渲染压力。

本次决定继续使用 Elasticsearch（ES），并采用组织树懒加载：

- ES 用于优化组织数据查询响应速度。
- 懒加载用于按需加载下级组织，避免首次加载整棵树。
- 组织树查询数据以数据库中的组织机构数据为来源；新增手动同步接口时，读取数据库全部组织机构并同步更新 ES 中的组织树数据。

## 二、组织树层级规则

组织树的根节点**固定为“浙江省”**，不因当前账号或角色变化而改变。

层级关系继续使用现有系统字段维护：

- `dept_id`：系统内部组织主键。
- `parent_id`：父部门 ID。
- `ancestors`：祖级路径。

组织树的父子关系必须根据 `dept_id`、`parent_id`、`ancestors` 等现有组织关系字段确定，**不能使用 `org_num` 作为组织树层级判断依据**。

示例结构：

```text
浙江省
├── 浙江省金融监管局
│   └── 杭州市金融监管分局
│       └── 萧山区金融监管支局
├── xx银行
│   └── xxx分行
│       └── xxx支行
└── xx银行
```

监管机构之间的层级按照监管机构数据及其实际父子关系维护。该层级规则与服务业务无关，不通过服务业务规则推断，也不要求所有银行机构都机械套用省、市、区行政层级。

## 三、机构数据字段与返回内容

组织树节点需要返回全部约定字段，不区分树节点和展开详情的字段精简模式。

需要返回的字段包括：

1. 机构名称
2. 机构号（业务机构编号）
3. 机构地址
4. 机构负责人
5. 负责人固定电话
6. 负责人移动电话
7. 机构经纬度
8. 所属网格
9. 上级机构
10. 机构类型（省/市/区/总/分/支）
11. 机构介绍

现有字段的初步对应关系：

| 展示字段 | 字段或数据来源 | 说明 |
|---|---|---|
| 机构名称 | `dept_name` | 现有字段 |
| 机构号 | `org_num` | 第三方系统对接编号，仅记录，不用于组织树层级判断 |
| 机构地址 | `address` | 现有字段 |
| 机构负责人 | `duty_name` | 现有字段 |
| 负责人固定电话 | `duty_telephone` | 现有字段 |
| 负责人移动电话 | `duty_phone` | 现有字段 |
| 机构经纬度 | `lng`、`lat` | 当前暂时没有可用经纬度数据 |
| 所属网格 | 后续根据经纬度进行落格计算 | 当前因暂时没有经纬度，暂不具备落格条件；不能直接把 `area_code` 认定为网格编码 |
| 上级机构 | 根据 `parent_id` 关联上级 `dept_id`，必要时利用 `ancestors` | 组织树关系沿用现有字段 |
| 机构类型 | 新增 `org_type` | 区分省/市/区/总/分/支 |
| 机构介绍 | 新增 `org_introduction` | 保存机构介绍 |

### 第三方对接编号

`org_num` 与新增的 `parent_org_num` 都用于记录第三方系统对接所需的机构编号信息：

- `org_num`：本机构的第三方机构编号。
- `parent_org_num`：上级机构的第三方机构编号。
- 两个字段仅用于记录和第三方系统对接，**不参与本系统组织树的父子关系计算，不影响现有功能逻辑**。
- 本系统组织树关系仍以 `dept_id`、`parent_id`、`ancestors` 为准。

## 四、数据库字段调整理解

用户确认新增以下三个字段：

```sql
ALTER TABLE `sys_dept`
    ADD COLUMN `org_type` varchar(20) DEFAULT NULL COMMENT '机构类型：省/市/区/总/分/支',
    ADD COLUMN `org_introduction` text COMMENT '机构介绍',
    ADD COLUMN `parent_org_num` varchar(100) DEFAULT NULL COMMENT '上级机构第三方机构编号';
```

以上 SQL 仅用于表达字段意图，正式实施前仍需核对当前表结构、字段类型及是否已存在同名字段；此阶段不执行 SQL。

新增字段约定：

- `org_type`：机构业务类型，取值对应省/市/区/总/分/支。
- `org_introduction`：机构介绍。
- `parent_org_num`：上级机构的第三方编号，仅记录，不替代 `parent_id`，也不参与树关系计算。

ES 中的组织树数据暂时按数据库字段同步，新增字段也应随数据库数据同步到 ES。历史数据中的 `org_type`、`org_introduction`、`parent_org_num` 由第三方提供，本系统不自行推断补齐。

## 五、现有接口改造范围

本次只修改 `SysDeptController` 中四个基础组织管理接口：

1. `GET /dept/list`：查询部门列表。
2. `POST /dept`：新增部门。
3. `PUT /dept`：修改部门。
4. `DELETE /dept/{deptId}`：删除部门。

以上路径已按当前仓库 `SysDeptController` 的实际映射核对。`/dept/list/exclude/{deptId}`、`/dept/selectDeptTree`、`/dept/pilotCenterPart/networkList` 等其他既有接口不在本次改造范围内；新增组织树查询和 ES 手动同步接口单独处理。

## 六、新增接口理解

### 1. 根据账号角色查询当前组织权限接口

目标是提供根据账号角色查询组织结构的接口，返回组织树数据。组织树根节点始终为浙江省。

角色及数据权限沿用项目现有 `@DataScope` 注解机制，不另行实现一套权限过滤逻辑。

另外，为后续“责任网点多分配”场景预留查询组织树接口的扩展空间；该场景本次暂不实现额外权限规则。

### 2. 手动同步 ES 组织树数据接口

新增一个手动触发的 ES 同步接口：

- 从数据库读取全部组织机构数据。
- 将组织机构数据同步更新到 ES 中的组织树索引。
- ES 字段暂时以数据库字段为准，新增的 `org_type`、`org_introduction`、`parent_org_num` 等字段也按数据库数据同步。
- 接口为 `POST /dept/es/sync`，无请求参数，响应沿用 `AjaxResult`。
- 每次全量读取数据库数据，构建新物理索引 `sys_dept_org_v1`，查询别名为 `sys_dept_org`，以 `dept_id` 作为 ES 文档 `_id`。
- 新索引构建及数量校验通过后原子切换别名；失败时保留旧索引和别名指向，清理临时索引并返回错误；切换后如有异常可切回旧索引。

## 七、懒加载与搜索规则

- 首次加载组织树时，只加载根节点或当前需要展示的首层节点，不一次性加载全部组织。
- 根节点固定为浙江省。
- 展开节点时，按该节点的系统内部组织 ID 查询其直接下级节点。
- 组织树的层级关系使用 `dept_id`、`parent_id`、`ancestors`，不使用 `org_num` 或 `parent_org_num` 计算父子关系。
- 懒加载查询需要支持按组织名称搜索。
- 搜索命中组织时，返回该组织及其**全部上级组织**，确保前端可以展示从浙江省根节点到命中节点的完整路径；不返回命中节点的下级节点。
- 每个树节点都返回本次约定的全部展示字段，而不是只返回精简字段。
- 接口使用 `GET /dept/tree`，可选参数为 `parentId` 和 `keyword`；未传二者时返回浙江省根节点，传 `parentId` 时返回直接下级，传非空 `keyword` 时只返回命中节点及其全部上级。响应沿用 `AjaxResult`，`data` 为节点数组。不新增子节点标识字段，不涉及前端改造，前端使用 `deptId` 和 `ancestors` 判断节点关系。

## 八、当前明确的范围与暂缓事项

### 已明确

- 继续使用 ES，并使用懒加载。
- 组织树根节点固定为浙江省。
- 组织层级沿用 `dept_id`、`parent_id`、`ancestors`。
- `org_num` 和 `parent_org_num` 仅用于第三方系统对接记录，不影响组织树功能。
- 新增 `org_type`、`org_introduction`、`parent_org_num` 字段。
- 现阶段只改四个既有接口。
- 新增根据账号角色查询组织树接口，以及手动同步数据库组织数据到 ES 的接口。
- 角色及数据权限使用项目现有 `@DataScope` 机制；新增组织树查询同样需要遵循当前用户的数据范围。
- 懒加载组织树需要支持名称搜索，搜索结果返回全部上级组织。
- 每个树节点返回全部约定展示字段。
- 经度、纬度由第三方提供；缺少经纬度及网格落格不属于本次业务改造范围。

### 暂缓或需在正式技术方案中细化

- 经纬度由第三方提供；缺少经纬度及网格落格不属于本次业务改造范围。
- 责任网点多分配场景的后续接口和权限规则。

## 九、现有 `@DataScope` 权限机制

已查看仓库中的实现：

- 注解位于 `kx-common/kx-common-datascope/.../annotation/DataScope.java`，可配置 `deptAlias`、`deptIdAlias`、`userAlias`、`userIdAlias`、`permission`。
- `DataScopeAspect` 在方法执行前读取当前登录用户，根据用户角色的数据权限规则生成 SQL 条件，并写入首个 `BaseEntity` 参数的 `params.dataScope`。
- 对应 Mapper SQL 必须引用该过滤条件，数据范围控制才会生效；后续实现需核对注解位置、SQL 别名和 Mapper 条件。
- 查询接口复用 `@DataScope` 控制当前用户的数据范围；新增、修改、删除继续保留现有的 `checkDeptDataScope` 等操作级权限校验，不以数据范围注解替代。

## 十、接口与 ES 约定

### 1. 空值格式

可空单值字段统一返回 JSON `null`；集合无数据返回 `[]`；不使用空字符串或字符串 `"null"` 表示空值。

### 2. ES 字段映射建议

- `dept_id`、`parent_id`、`ancestor_ids`：数值类型。
- `ancestors`、`org_num`、`parent_org_num`、`org_type`：`keyword`。
- `dept_name`：`text`，附带 `keyword` 子字段。
- `org_introduction`：`text`。
- `lng`、`lat`：`double`；无有效坐标时不参与坐标计算。
- 懒加载按 `parent_id` 查询直接子节点；名称搜索查询命中节点，再按 `ancestor_ids` 还原并排序上级路径。

## 十一、当前阶段结论

本次改造是在保留现有组织关系模型的基础上，继续使用 ES 并引入懒加载，优化组织树查询和页面加载。树根固定为浙江省，层级关系继续依赖 `dept_id`、`parent_id`、`ancestors`；`org_num` 和 `parent_org_num` 仅作为第三方对接记录，不参与层级判断。现阶段只修改 `GET /dept/list`、`POST /dept`、`PUT /dept`、`DELETE /dept/{deptId}` 四个基础组织接口，新增组织树查询接口和手动同步 ES 接口；支持名称搜索并返回全部上级组织，每个节点返回全部约定字段。

本文已补充当前确认的接口、ES、全量同步、搜索结果及空值约定；正式需求文档为主要验收依据。

## 十二、补充确认：扫楼上报与线索上报查询权限

本次不是只改组织树。组织树原有设计保持不变，同时需要为以下两个页面的相关查询接口设计权限兼容：

- 扫楼上报管理：`BuildingSweepReportController`，路径前缀 `/building-sweep/report`。
- 线索上报管理：`RiskClueReportController`，路径前缀 `/risk-clue/report`。

### 1. 金监机构用户

- 按当前金监机构关联的网格编码查询。
- 一个金监机构支持关联多个网格编码，两个页面均应查询这些网格范围内的相关事件。
- 不限于当前金监机构自己提交的事件。
- 本次这两个页面的权限依据是网格编码，不是行政区划管辖区编码。

### 2. 银行机构用户

- 查询当前所属银行机构及其全部下级银行机构对应的事件。
- 下级机构按系统内部组织关系识别，不使用第三方机构编号推导。
- 不得查询其他无关银行机构的事件。

### 3. 接口设计范围

设计阶段需要核对上述两个 Controller 下由页面实际调用的查询接口，包括列表，以及页面实际使用的详情、统计、报表或导出查询。服务端必须执行权限过滤，不能只依赖前端隐藏数据，也不能允许客户端通过传入其他机构或网格参数扩大权限。

若现有数据模型不能关联金监机构与多个网格编码，或不能关联上报事件与网格/银行机构，应列为待核实的设计依赖，不得假定相关字段已经存在。

### 4. 本次边界

- 组织树结构、ES、懒加载、搜索及原六个组织接口的设计不变。
- 本次只补充扫楼上报和线索上报两个页面相关查询接口的权限设计。
- 本阶段只修改设计文档，不开发代码、不执行数据库变更。
- 现有 `@DataScope` 是否能表达两类规则需要结合实际 SQL 和数据关联核实，不能默认注解本身已满足要求。
